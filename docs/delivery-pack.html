2Two surfaces, one pipeline

The split is not by SDLC phase. It is by who is acting.

App = where a human decides or reads. CLI = where an agent executes.

The review gate is the hinge. Upstream of it the work is app-led because humans are directing. Downstream of it the work is CLI-led because agents are executing and nobody is watching.

3Cache-efficient prompt architecture

A cache read costs roughly a tenth of a fresh input token and an eighth of a cache write. The design target follows: a long identical prefix, reused across many calls, with only a small task delta changing.

Prompts assemble in fixed order, most stable first

rulesIdentical for every call in the reposystem
roleIdentical for every call of one stagesystem
memoryIdentical within a run, slow-changing across runsprompt
refChanges between work types, not within a runprompt
taskThe only layer that genuinely changes per callprompt

Providers cache a prefix: put a volatile segment early and everything after it is a miss, however stable. Ordering by stability makes that prefix as long as it can be — the entire mechanism. Plain string assembly; a provider that does no caching is unaffected.

Why this landed in Sprint 0 rather than later

The cache key hashes the assembled prompt by design, so reordering layers invalidates every committed recording at once. At the rework the repo had zero LLM callers and zero recordings — the only point at which the change is free. Prefix order is frozen from Sprint 3 onward, and a test pins it so a change cannot be silent.

Measured or unset — never invented

cache ratio, provider reported nothing : None
cache ratio, reads but zero writes     : None
cache ratio, 1000 reads / 100 writes   : 10.0

Zero is a measurement; None is an admission. A provider that cannot report cache counters must not look like one that measured a total miss. Applying this found and fixed two latent bugs: a fabricated 0 when a provider returned no usage object, and a summary collapsing “nobody reported” into “everybody reported zero”.

What was adopted from the architecture review

5Delivery stories

The three stories the gate unlocks, exactly as the console renders them. Each carries its own provenance badge, stream routing and acceptance criteria.

3 stories · 29 points total · broken out of EPIC-S7-001 after human review.

S7-001-1 staged

Identify the member and confirm their details

As a plan sponsor benefits administrator, I want to identify a member from the policy number and member id I already hold and see the details MapleSure holds for them, so that I do not re-key information that has already been recorded and introduce errors.

FrontendAPI / ServicesSystem of record8 points
Acceptance criteria
  • AC1 — Given a valid policy number and member id for a member my organization sponsors, the member and plan details held against that record are displayed for confirmation.
  • AC2 — Given a member my organization does not sponsor, no member detail is disclosed and the submission cannot proceed.
  • AC3 — Pre-populated details are presented for explicit confirmation and are not treated as attested until I confirm them.
Assumptions to validate with an SME
  • The exact set of pre-populated fields is unvalidated — EPIC-S7-001 §10.
  • Assumes the T5 system-of-record field addition lands; until it does, this story is verifiable only against a stubbed lookup.
S7-001-2 staged

Capture the claim details and attach supporting documents

As a plan sponsor benefits administrator, I want to enter the disability claim details and attach the supporting statements in one place, so that MapleSure receives a complete packet instead of documents that arrive detached and have to be matched by hand.

FrontendAPI / ServicesDatabase13 points
Acceptance criteria
  • AC1 — Claim details required to open an intake file can be captured against the confirmed member.
  • AC2 — Multiple documents can be attached to a single submission and remain associated with it.
  • AC3 — Attachments are subject to the existing file type and size policy, and a rejected file explains why.
  • AC4 — An in-progress submission survives a dropped session and can be resumed.
Assumptions to validate with an SME
  • Which attachments are mandatory versus optional at submission time is unvalidated — EPIC-S7-001 §10.
  • Whether a partial submission may be saved and completed later is unvalidated; AC4 assumes it may.
S7-001-3 staged

Confirm receipt and expose submission status

As a plan sponsor benefits administrator, I want an immediate reference for my submission and a way to see where it sits afterwards, so that I stop phoning the service desk to ask whether it arrived.

FrontendAPI / ServicesDocument intake8 points
Acceptance criteria
  • AC1 — On submission I receive an unambiguous confirmation carrying a reference I can quote.
  • AC2 — The submission reaches intake as a single associated packet.
  • AC3 — I can later see the status of submissions my organization made, and only those.
  • AC4 — Every submission records who submitted it, when, and what was attached.
Assumptions to validate with an SME
  • The authoritative status values, and who may see each one, are unvalidated — EPIC-S7-001 §10.
The assumptions are part of the deliverable

Each story carries what it is assuming, not only what it asserts. All three name a point still awaiting SME validation, and S7-001-1 additionally depends on a system-of-record field addition that is a manual change outside this delivery team — until it lands, that story is verifiable only against a stubbed lookup. This is the dependency that makes the coverage figure honest rather than decorative.
